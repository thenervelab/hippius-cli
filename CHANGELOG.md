# Changelog

All notable changes to `hipc`, named `hip` up to 0.14.0, are listed here. The format
follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the version follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.16.0] - 2026-11-12

### Added

- `hipc billing gamma` pays with the Bittensor gamma of subnet 75, through `/api/billing/gamma/`. `get` prints the Hippius spender a deposit must name, the minimum, and each linked hotkey with its deposit read from the chain. `hotkeys create --hotkey-file <path|->` links the hotkey whose BIP-39 words the file or stdin holds: it asks for the challenge, signs it with the hotkey's sr25519 key only when the message is exactly the API's link template for that hotkey, sends the signature, and clears the keys; the file is held to the config file's checks, and no message quotes a word. `hotkeys delete <hotkey>` unlinks one and is confirmed. `conversions create --hotkey <SS58> --amount <GAMMA>` burns gamma for the same amount in USD, is confirmed, and names the read that follows it; `--amount` is at least `0.1` with at most 9 decimals, checked before anything is sent, and an answer without a conversion id is `partial_failure` with the answer on stdout. `get` also prints `service_hotkey`, the hotkey `btcli gamma mint` takes to name the spender. `conversions list` pages like the other lists (`--limit`, `--page-token`, `--all`), and `conversions get <id>` reads one conversion. The API's `gamma_unavailable`, `gamma_personal_only`, `gamma_hotkey_not_found` and `gamma_conversion_not_found` refusals get a hint that names what helps. The routes act on the signed-in user's own account, so a membership is refused, as on the hAlpha routes. A dry run of the link reads the words, to name the hotkey, and lists both requests with placeholders.
- `hipc schema` lists, for each command, the `routes` it may send to: each one's `method` and path template, such as `{"method": "GET", "path": "/api/compute/vms/{vm_id}/"}`, with a placeholder in braces for each value the command fills in, and `{name..}` for a value of more than one segment, such as a Hub repository. `hipc api`, which sends to the route it is given, lists the routes `hipc` knows that only it reaches (an account deletion request and its withdrawal, a network isolation change, an App Engine compose update, and an operator node's storage), and a command that sends nothing lists none. `schema_version` is now `4`.
- When an answer says its route is deprecated, with a `Deprecation` (RFC 9745) or a `Sunset` (RFC 8594) header, `hipc` prints a `warning:` that names the route and the dates the headers give, and in JSON adds the text to `warnings`; the command does what it did before. A `410` answer, a route the API has retired, gets a hint to upgrade `hipc`. TENETS tenet 15 says so.

### Changed

- The HTTP library is ureq 3.5. A user name or password in a proxy variable's URL (`HTTPS_PROXY=http://user:p%40ss@proxy:3128`) is now percent-decoded once before it is sent to the proxy, so a literal `%` in it must be written `%25`; a user name or password that decodes to invalid UTF-8 is refused with exit 2 `usage`, as a proxy URL the library cannot parse is.
- The SHA-256, SHA-512, PBKDF2, and BLAKE2b crates move to their current releases. Every address, key, and SHA-256 hash stays byte for byte as before, which known-answer tests check. The HMAC and SHA-512 state of a gamma hotkey's key derivation is now cleared from memory when dropped.
- A confirmation question discards what was typed at the terminal before it was shown, and reads its answer without keeping what follows the line, so a `y` typed while an earlier read ran, or the second line of a paste that answered an earlier question, no longer answers a question the person has not seen.
- `hipc auth login` without `--token-file` asks about a non-default API origin before it asks for the token, so a person sees where the token goes before pasting it. The question says the token is asked for next, at the hidden prompt. A dry run without `--token-file` asks for no token: `replaces_token` says whether the profile stores one.
- `hipc support tickets create` and `reply`, and a support write through `hipc api`, also refuse a text that holds an access key (12 to 24 words in a row on the BIP-39 list whose checksum holds, with punctuation and numbering between them read as spaces), and find the API token when whitespace splits it or when it is split between the subject and the message. The help says the check catches an accident, not a secret encoded on purpose.
- `hipc api` applies `--public`, `--remove-others`, and `--change-isolation` to every write method of a guarded route, not only the one the API documents: a `PUT` of `/cdn/zones/<zone_id>/` that moves the origin needs `--public` as the `PATCH` does, and a `PUT` or `PATCH` of `/network/isolation/` needs `--change-isolation`. A `PUT` borrowed from a body-conditional rule needs the flag whatever its body sets, since it replaces the whole resource. A `POST` or `DELETE` of `/cdn/lists/<name>/items/`, which adds or removes the items it names, needs no flag. A refusal holds for every write method too, its message naming the method sent: a `PUT` of a CDN hostname's `dns-setup/` or of `/registry/subscribe/` is refused as its `POST` is, but a `DELETE` of `/account/deletion/`, which withdraws a pending request, is sent. A `--public` refusal of a `PUT` of `/registry/me/publicity/` names the Hub namespace it may open, as the `PATCH`'s does.
- The secret, provisioning, permanent-delete, flag, and refusal tables `hipc api` checks match a path in any letter case (a mixed-case path of an account-scoped route is still refused, as an unlisted route is), so `GET /Network/me/`, which may create the network, asks as `GET /network/me/` does, and a flag rule holds for `/CDN/zones/` too.
- An error body drops `password`, `secret_key`, `secret_access_key`, `aws_secret_access_key`, `private_key`, `access_key`, `api_key`, `api_token`, `session_token`, and `passphrase` from `details` with the other secret fields, each in any letter case and with `_`, `-`, or nothing between its words; a secret field whose value is a list of validation messages stays. A body that is one JSON string, such as `"Rate limit hit"`, is quoted in the message as `the API says ...`.
- An S3 token answer that names its secret `secret_key`, `secretAccessKey`, or another spelling of the secret access key is treated as `secret`: `--secret-file` moves it, `--reveal` prints it as `secret`, and a list drops it.
- A Hub key or robot answer that holds a `docker login` command and whose `--secret-file` cannot be written prints only the secret, rather than the whole answer with the command in it.
- A token on the command line is not repeated in an error: a word that could not be a command name after `hipc auth` or one of its commands, which take none, a token the run knows (`HIPPIUS_TOKEN` or a stored one) anywhere on a command line `hipc` refuses, and the path of `--token-file`, `--secret-key-file`, or an invite's `--token-file` when it names no file. A path that holds a seed phrase is named by its flag in every message, and a missing `--hotkey-file` path is not repeated. A word of 20 characters or more that a usage error would quote, given to any command as an argument, a value, or a command name, is not repeated; outside `hipc auth` the hint names the command's help. A stored or `HIPPIUS_TOKEN` token shorter than 12 characters is no longer looked for in a command line or a support ticket.
- A document is printed as a dry run, with `confirmation` and `confirmation_when`, only when the run was given `--dry-run`; a server's answer with `dry_run` and `requests` fields is printed as it came.
- `hipc billing top-up --method halpha` refused for an account that signs its own buys (`self_sign`, or `custodial` false in the quote) now says that such buys are made in the console and that a card or Bitcoin top-up works with `hipc` too, and its hint names the console at `https://console.hippius.com`, in place of saying `hipc` cannot sign them yet. `hipc` never signs with an account's own key.
- `hipc auth login` while `HIPPIUS_TOKEN` is set stores the token and, in text mode, warns that later commands still send the variable, not the token just stored.
- A command line that holds 12 or more BIP-39 words in a row is refused as holding what looks like a seed phrase, and the hint says to sign in with a console token, and to pass a Bittensor hotkey's words only in the file `--hotkey-file` names. The no-token hint names only a token created in the console's settings.
- `hipc s3 tokens list` is documented as a list read whole on purpose (tenet 6 and its help): it prints the master and the sub tokens of two routes as one list, follows every page of each within the caps `--all` has, and takes no page flags. Its behaviour is unchanged.
- The help of `hipc cdn rules update`, `hipc account members update --grant`, and `hipc cdn lists items update` says that the route takes no version, so a change someone else makes between the read and the write is lost; for a member, a grant revoked in that window comes back if a `--grant` names it.
- The `hipc compute app-engine apps create` question says that stored backups are billed per GB-hour at the price `hipc compute backups options` shows, and names where the OS disk tier's price is shown, as the `hipc compute vms create` question does. The `hipc compute backups policy update --failover auto` question says, as the launch questions do, that what was written after the latest backup is lost; one clause now serves all three. An App Engine launch that sent secrets keeps a kebab `code` in a refusal's `details` and message, as it keeps `error`.
- A placement group (`--placement-group` of `hipc compute vms create` and `hipc compute app-engine apps create`) and a node pool name (`hipc compute kubernetes node-pools create --name`) that start with `-` are refused as `usage`, as a Hub namespace, a Hub key name, and a bucket name are, so a command that names them later never has a flag-shaped word to work around. Ids the server issues, such as a VM id, are still taken with a leading `-`.
- `hipc` accepts a config file key it does not know, at the top level, in a profile, or in a profile's `hub_subscribe`, such as one a newer `hipc` wrote: it keeps the key when it rewrites the file, and warns once per run where the file holds one and the command reads the file (`hipc version`, `schema`, and `completions` do not), in text mode on stderr and in JSON in `warnings`, without naming the key or its value. Such a file used to fail every command with `usage`. TENETS tenet 8 says so.
- `hipc compute runners settings update --max-concurrent 0` needs `--yes`, as a raise does, unless the setting is already `0`: the server does not document what `0` means, and it may mean no cap. The help says the read of the settings and the write are separate requests. An update with no setting is refused by the parser, and `hipc schema` lists the five settings as a required group.
- `hipc cdn zones update --prefix` without `--bucket` reads the zone and sends its whole `origin`, its `kind` and `bucket` with the new `prefix`, which is right whether the API merges `origin` or replaces it. The dry run lists the read, then the `PATCH` with placeholders; a zone whose `origin` has no `bucket` is `internal`, with a hint to pass `--bucket`. The question names that bucket as the zone's own (`its bucket`), not as a change.
- `hipc compute firewall update --remove-others` without `--base-revision` reads the rules after the question and sends their `revision` as `base_revision`, so a rule another client adds in between makes the update a `conflict` rather than being deleted; the dry run lists the read. That read takes only the `revision`, so a rule in the list that `hipc` does not read does not stop the update. The conflict's hint says to run the command again.
- `hipc hub namespace get` and `status` drop every spelling of a robot secret at any depth, as `hipc hub namespace robot get` does, and print nothing of an answer that holds a `docker login` command (`internal`).
- The `402` hint of `hipc hub namespace create` names no amount: the server sets the minimum balance, and the hint names `hipc billing balance` and `hipc billing top-up`.
- `hipc cdn estimate --traffic` sends the region in upper case, as every compute region is sent, so `--traffic FR=1 --traffic fr=2` is refused as one region given twice.
- `hipc cdn zones create --name` and `hipc cdn zones update --name` take one line of 1 to 64 characters, checked before the question.
- `hipc compute kubernetes node-pools create --taint` refuses a key or a value that holds `:`.
- `hipc compute databases restore --target-time` takes a lowercase `t` and `z`, as RFC 3339 allows, and sends them in upper case; a time the API answers is read the same way.
- `hipc schema` and `hipc api --help` state each refusal of `hipc api` exactly: a refusal listed for one write method holds for every write method, so a `PUT` or `PATCH` of `/api/account/deletion/`, any write of a DNS setup or of `/api/registry/subscribe/`, and any write of `/api/compute/app-engine/apps/` with `secrets` are named. The support check is described as it runs, a token split by an invisible joining character and an access key included, in `hipc api`'s row and in the `support tickets create` and `reply` rows. The help of each `hipc billing top-up` flag that one `--method` takes names it.
- In JSON mode, the warnings of a result with no place for a field, the array `--all` prints or a `hipc api` body, go on stderr as one `{"warnings":[...]}` object; they were dropped. The result keeps its shape. TENETS tenet 15 says so.
- A note's next command, and the `next_step` that carries it, quotes a `--profile`, `--api-url`, or selector value a shell would split or expand, an empty one included, and joins a value that starts with `-` to its flag with `=`, rather than leaving the command out. A value with a character outside printable ASCII still leaves it out.
- TENETS tenet 5 lists the hAlpha top-up's `reads_first`, its read of the quote, and tenet 9 says that a JSON number `hipc` redacts becomes the string `"<redacted>"`.
- A field name in a redacted answer or error (the API token in an error, an invite token, a DNS credential, a database credential `--credentials-dir` moved, App Engine secrets) is replaced whole by `<redacted>` when it is one of the redacted values or holds one of eight characters or more, as App Engine launch output already did. A field name that holds only a shorter value is kept as the server wrote it, as a number is, where before a name was redacted character by character.
- `hipc api` treats a route that no command lists in its `routes` as one it does not know: a `GET` of it needs `--reveal`, since its answer may hold a secret, and a write still needs `--yes`, as any write does, and warns that `hipc` does not know what it changes, on stderr in text mode and in `warnings` in JSON. `reveal_when` and `confirmation_when` of `hipc api` in `hipc schema`, the `--reveal` help, and TENETS tenets 7 and 9 say so.
- The route table decides each request to a route a command sends: its account, project, and billing headers, whether its answer holds a secret, whether a read creates something, whether it cannot be undone, and what `hipc api` asks before sending it. The path tables decide only a route no command sends. A `HEAD` counts as the `GET` of its route, so a `HEAD` of an S3 plan read takes the selected project as the `GET` does. The `--reveal` help of `hipc api` names each placeholder by what fills it, such as `/registry/keys/<key_id>/rotate/`.
- `hipc api` treats the routes it guards but no command sends as routes it knows, so a write of them no longer warns that `hipc` does not know it: the withdrawal of an account deletion request (`DELETE /account/deletion/`), a network isolation change, an App Engine compose update without `secrets`, and an operator node's storage. Their guards are unchanged.
- The help of `hipc api` and its `--change-isolation`, `--public`, and `--remove-others` flags, and `confirmation_when`, `refused_when`, and each guard's `when` on `api` in `hipc schema`, are written from the route table, so each names every route it applies to by its method and path: a flag's guard lists each route as "a `PUT` of `<path>`", with the condition on its body, and says which write methods of a route need none. The routes `hipc api` never sends are each named with their reason and the command to run instead. The wording of those texts changes; what is refused, guarded, or confirmed does not.
- The `hipc compute app-engine apps create` question says that the OS disk tier is fixed for the VM's life, as the `hipc compute vms create` question does: one clause serves both.
- An App Engine launch wait that runs out of time while the app's boot is stalled (`boot_stalled`) says so in its `timeout` message, as a VM launch wait does: the two launches share one wait.
- `hipc cdn cap update` and `hipc compute runners limit update` ask one question, built one way. A runner cap set over a limit with no amount says "where the cap in force is unknown", as the CDN cap did, and a CDN cap set over a cap `hipc` cannot compare says the zone may spend more if the cap in force is higher than it shows, as the runner cap did, rather than that it will.
- The help of `hipc compute runners limit update` says that the read of the limit and the write are separate requests, since the route takes no version, so a change someone else makes between them is not seen; `hipc billing auto-reload update` says so in the same words.
- The S3 plan (`hipc s3 subscription subscribe` and `change --plan`), the backup interval (`hipc compute backups policy update --interval`, and `--backup-interval` of `hipc compute vms create` and `hipc compute app-engine apps create`), the database tier, size, and engine version (`hipc compute databases create`), the runner size (`hipc compute runners settings update --allowed-size`), and the Hub key role (`hipc hub keys create --role`) take any code the server may add, not only the ones this `hipc` knows: a code is one word of lowercase letters, digits, `.`, and `-` (an interval, a whole number of seconds above 0), and the help lists the codes known today. A backup policy update, and a VM or App Engine launch with `--backup-interval`, read the backup options after the question (`GET /api/compute/backup-options/`) and refuse an interval they do not list as `usage`, before anything is sent or launched; their dry runs list the read, and `hipc schema` lists its route. An S3 plan purchase or change sends the code as given, and the server judges it. `hipc schema` no longer lists `possible_values` for these flags.
- A bucket name, an S3 token id, and a Hub namespace name are checked when the command line is read, as every other id is, so a bad one is refused before the config file is read, with the refusal every value check gives (``invalid value `a..b` for `<BUCKET_NAME>`: a bucket name is ...``).
- Every one-line label `hipc` checks before it sends one follows one rule: a project or billing account name, a referral link's name, an SSH key's name, a support ticket's subject, a network peer's name, a CDN zone's name, and now the text fields of `hipc billing profile update`. Each holds no control character or line break and no character that changes how text reads without being seen, such as a bidi override; a referral, SSH key, ticket, peer, or zone name with one was sent before. `--billing-email` takes an address, as an invite does, or empty for the account's own.
- A whole number on the command line (a numeric id, a quota limit, a storage cap, a node pool size, a WAF zone count) is plain digits, as a page token already was: `+7` is refused. Every amount (credits, US dollars, hAlpha, gamma) is read with one grammar, and a CDN spend cap that is not one is refused as "a monthly spend cap is a decimal number of credits", as a runner cap is.
- The help of `--reveal` reads the same on every command that issues a one-time secret, and the launch flags `hipc compute vms create` and `hipc compute app-engine apps create` share (`--placement-group`, `--os-disk-tier`, `--backup-interval`, `--failover`, `--on-guest-poweroff`, `--wait`, `--no-wait`, and `--wait-timeout`) have one help text, the VM launch's, shown by both.
- `hipc api` holds a route's refusal, its `--public`, `--remove-others`, and `--change-isolation` rules, its `--reveal`, and its question for a read that may create something or a delete that cannot be undone under every API version of its path, with or without a version segment, so `POST /v2/auth/token/` is refused as `POST /auth/token/` is. Such a path is still a route `hipc` does not know. TENETS tenets 5 and 9 say so.
- A route whose path names a project or a billing account by its id (or `default`), or a Hub model by its two-part name, is no longer reached by a path with another value there: `PATCH /accounts/projects/bulk/` reaches no route `hipc` knows, so `hipc api` warns about it, and a stored project or billing account is refused on it rather than left off. `GET /models/<namespace>/<repository>/<reference>/` reaches the model version's route rather than the model's.
- In `hipc schema`, the paths that `hipc api`'s `refused_when`, `confirmation_when`, and each guard's `when` name write a placeholder in braces, `/api/cdn/zones/{zone_id}/`, as `routes` does, so a guard's path matches a route as written; the help keeps `<zone_id>`.
- `hipc api GET <path> --all` on a route that pages by number without `next` links, such as `/models/`, exits 1 `internal` when a page says more remain, rather than printing the first page as the whole list. A page of such a list, through `hipc hub models list` too, that holds fewer items than its `total` places on it is `internal` too, as an empty one was.
- An error that repeats a value the request sent under a secret field no longer prints it when the value is a number, or a string or number nested in an object or a list under that field: each is replaced by `<redacted>` in `details` and the message, as a string value already was.
- The PyPI package is now `hippius` (`pip install hippius`, `uv tool install hippius`, or `pipx install hippius`), not `hippius-cli`; the command it installs is still `hipc`. The release workflow builds and uploads the wheels to the PyPI project `hippius` when the repository variable `PYPI_PUBLISH` is `true`. The README, `docs/getting-started.md`, `docs/agents.md`, and the wheel's own README say so.
- The README and `docs/getting-started.md` say that the PyPI project `hipc` is unrelated to Hippius; the README says the install script checks the release signature when `cosign` is installed, and `HIPC_INSTALL_REQUIRE_SIGNATURE=1` makes that required. `docs/README.md` no longer promises a CLI section on docs.hippius.com with the release.
- The release tarballs are reproducible: `scripts/package.sh` packs each with its members in a fixed order, owned by `0:0`, with fixed modes and the commit's time, and gzip storing no name or time; the binaries are built with the checkout and cargo paths remapped, on pinned runner images. The release runs the arm64 macOS binary before it is packed, as it runs the Linux ones, and every workflow job has a timeout.
- `scripts/manual_test.sh` checks the token with `hipc auth status` before the first scenario, says it came from `HIPPIUS_TOKEN`, and stops with one failure when it is refused. An account with no Hub namespace is the state `hub_unprovisioned`, as an account with no private network is, and not a failure. The account and balance comparisons are no longer a pass when a snapshot read failed or gave no balance: offline they are skipped, and online a missing balance fails. `--offline` refuses to run when something listens on its dead origin.

### Removed

- `hipc auth login --access-key` and `--access-key-file`, and `--new-account` with them, are gone: `hipc` no longer signs in with an account's 12-word access key, and each flag is now a plain `usage` error (exit 2). Create an API token in the console at https://console.hippius.com/dashboard/settings (an account that signs in with a 12-word access key gets its token from the access-key sign-in described at https://docs.hippius.com/use/wallet-login) and use `hipc auth login --token-file <path>`, or paste it at the prompt of `hipc auth login`. The `refused_when` of `auth login` in `hipc schema` is now `null`, and the `secp256k1` and `sha3` crates are no longer built. The `billing gamma` hotkey file is read and signed as before.
- The hints for flags renamed and commands moved before 1.0 are gone. An old flag (`hipc api --input`) or an old command path (`hipc hub namespace provision`, `hipc network groups` alone) is now a plain `usage` error whose hint is the help of the command it reached, as any unknown word is.

### Fixed

- `hipc hub usage --repositories` reads the answer the API sends, `{page, page_size, repositories}` with no `next` link and no total, and follows each full page to the next one until a page is short, printing every repository as one list with `next_page_token` null. Before, every run exited 1 `internal`, saying the answer was not a list. A page that does not give its `page` and `page_size` is `internal`, so a short list is never printed as the whole one.
- `hipc account projects transfer` reads the accounts answer as `hipc account list` does, so an answer without an `accounts` list is named as such (`internal`), not as one that marks no account as the token's own.
- Text mode prints a `get` whose answer holds `items` and `next_page_token` as the one object it is, with no table and no `next page: --page-token` hint, which the command does not take. Only a command that prints a list envelope prints a list, and only its empty list gets the `no items` note.
- Every redaction of several values at once (the spellings of the API token in an error, a credential `--credentials-dir` moved out of a database answer, a DNS credential `hipc cdn hostnames dns-setup` sent, and App Engine secrets) finds every place each value matches first and writes one `<redacted>` per span of matches that overlap. So a short value no longer cuts the marker a longer one wrote or a longer value that holds it, and two values that overlap in the text no longer leave part of either shown.
- A list's envelope, a dry run, and every document `hipc` takes a field out of keep the server's other fields in the order it sent them. With `serde_json`'s `preserve_order`, `Map::remove` moved the last field into the gap; a lint now refuses it.
- `hipc s3 configure` locks the AWS config file as well as the credentials file, so two runs that share only the config file cannot lose each other's profile. When another run holds a lock, text mode prints a `note:` that names the file before it waits; JSON mode waits without a word. The same note covers the lock of the hipc config file.
- `hipc s3 configure` reads section headers as botocore does: a line indented under an option continues that option's value and is not a header, and in the credentials file `[profile default]` is a profile of that name, not `default`. In the config file, `[profile <name>]` is split as botocore splits it, so `[profile "x"]` is `x`.
- A new `~/.aws` or `~/.hippius` directory and a new AWS file get mode `0700` or `0600` whatever the umask, and a lock file is opened read-only: under `0277` they were read-only, and a later run could not write the profile or take the lock.
- `hipc compute kubernetes clusters kubeconfig`, `node-pools scale` and `nodes replace` compare the cluster's public keys with the key file's as the bytes they decode to, so a cluster whose answer spells a key in another base64 form (URL-safe, without padding, or wrapped) is no longer refused as another cluster's.
- `hipc compute kubernetes clusters kubeconfig` picks the newest launch drop by its `created_at` time, so a time with a fraction is no longer older than the same second without one, and passes over a drop without a ciphertext or a signature for the newest one that has both.
- An RFC 3339 time with a day its month does not have (`02-31`), an offset past `23:59`, or a field of the wrong width no longer reads as a time; the hAlpha in-flight check treats such a `created_at` as it treats any unreadable one, as in flight.
- The hAlpha top-up's in-flight check measures a purchase's age by the earlier of the local clock and the `Date` of the purchases read, so when the API sends a `Date`, a local clock that runs fast no longer ages a purchase in flight out of the 15-minute window and lets a second buy through. A local clock set before 1970 is `internal`, whatever the `Date`.
- The VM launch wait, the App Engine launch wait, and the hAlpha purchase follow wait for the server's `Retry-After` after a retryable failure, when it asks for longer than their interval; one that runs past `--wait-timeout` ends the wait at the deadline without another read. The three share one loop.
- `hipc account projects delete` clears the stored project only if it is still the archived one when the config file is locked, so a `hipc account projects use` another run stored meanwhile is kept.
- `hipc compute vms create --open-port` sets the rules on a launched VM whose id starts with `-`. Every command a VM hint or warning prints (the failed rules update, `public-ip create`'s inbound warning, the firewall `409` hint, and the exposure `404` hint) puts such an id after `--`, so it runs as written.
- An App Engine 403 that carries `app-engine-unavailable` in `code` rather than `error` gets the hint to run `hipc compute app-engine get` too.
- `hipc s3 configure --dry-run` is refused, as the real run is, when `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` name one file in a directory that does not exist yet; before, only the real run refused it, after creating the directory.
- `hipc s3 configure` that cannot create the AWS credentials file no longer leaves the empty config file it created for the profile.
- `hipc s3 configure` keeps the blank and comment lines that end a profile section it replaces, such as `# work account` above `[profile work]`, which describe the section after them.
- `hipc auth login` with the token a profile stores with spaces around it, from a hand edit, no longer takes it for another token and asks for `--yes`.
- A wait (a VM or App Engine launch, a hAlpha purchase) whose retryable failure carries a `Retry-After` shorter than its interval sends its last read before the deadline, as it does without the header.
- A note no longer names a next command with an empty `--profile` or other empty global value unquoted, which a shell would read as the next word.
- An error answer whose body cannot be read, or is larger than 32 MiB, keeps its status's code and says in its message that the body was not read, rather than reading as an answer with no body. TENETS tenet 3 says so.
- A failure whose record of what was done cannot be written to stdout, other than to a closed pipe, is `internal`, as any other stdout write failure is, and its message names the failure it replaces; before, the record was lost without a word.
- Backspace at the hidden token prompt erases the last character whole, not its last byte.
- A note after `hipc hub namespace create` no longer says no `robot_secret` was issued, or suggests the rotate that would replace it, when the answer holds the secret under another of its names, with or without `--secret-file`; the `docker login` note names the field the secret came in.
- A redacted all-digit value no longer turns a number into `<redacted>` when only zeros differ: numbers are compared with it by value, so a value `1000` leaves the counts `1` and `10` as they are.
- In JSON mode, a document that holds a `warnings` field of its own, such as a server answer's, keeps it as it came: the run's warnings go on stderr as one `{"warnings":[...]}` object, as they do for a result with no place for a field, rather than replacing the server's. TENETS tenet 15 says so.
- `hipc billing top-up --method halpha --amount` takes trailing zeros past the 18th decimal, as a credit amount does, since they hold no value.
- A list answer that names its next page in `next_before`, `next_cursor`, or `cursor` and has no `next` link, where `hipc` reads a `next` link (a list command's page, a list read whole, or `hipc api --all`), exits 1 `internal` rather than being printed as the whole list. TENETS tenet 6 says so.

### Security

- More copies of secrets are cleared from memory when they are dropped: a secret read from `--token-file`, `--secret-key-file`, or an invite's `--token-file`, now read into a buffer of its full size, and from stdin without the standard library's buffer; the S3 token document `--from-token-file` reads; the S3 secret key and the AWS credentials text read and written; the one-time secret `--secret-file` moves; the DNS credential's redactions; every field of a DNS credentials, app secrets, or cluster key file, on every refusal; and the text an error held before a secret was redacted from it.
- The password and TLS key of a new database are cleared from memory when `hipc` is done with them, and so are the copies of the credentials `--credentials-dir` writes to its files.
- A path given to `--credentials-file`, `--secrets-file`, or `--cluster-key-file` that names no file is no longer repeated in the error.
- Every command line is checked for what looks like a seed phrase or a known API token before the command runs, not only one that fails to parse, and is refused without being repeated. A value that `--profile`, `--aws-profile`, or `--access-key-id` refuses is no longer repeated in the error. The seed phrase check reads anything that is not a letter as a space, so words joined to their flag with `=` or numbered are found too, and a value of 20 characters or more that a flag's check refuses is not repeated in the refusal.
- Text mode escapes U+180B to U+180D, U+180F, U+17B4, U+17B5, and U+2800, which print as nothing.
- The database credentials `--credentials-dir` moves to files are redacted from the rest of the answer in every spelling `hipc` redacts a secret in, percent-encoded included, and the file paths the document names are never redacted.
- The copies of the DNS credential in the `hipc cdn hostnames dns-setup` request body are cleared once the body is serialized.
- The database credentials `--credentials-dir` moves to files are redacted from the field names and numbers of the rest of the answer too, as tenet 9 says: a number that is one of them becomes the string `"<redacted>"`.
- The request body of an App Engine launch and of a DNS setup is cleared from memory when the request is dropped, and so is the token each profile of the config file stores.
- A validation message kept under a secret field of an error body, such as `{"password": ["... is too common."]}`, has every value the request sent in a secret field redacted from it.
- An error body drops a field whose name ends as a secret field's name does, in camelCase too, such as `authToken`, `APIKey`, or `newPassword`, as it drops the spellings it listed before; a bare `token` stays, as before.

[y/N]``, naming the account under a membership) and sends `POST apps/`. `--secrets-file` is one JSON object of name to string, held to the config file's checks (owner only, no bits for the group or others, not a symlink, at most 1 MiB, in a directory no one else can write); there is no stdin or argv form, and values are sent exactly, nothing trimmed. A dry run lists both requests, with `<the NAME from --secrets-file>` for each value; `--debug` prints no body; every value, in each spelling, is redacted from the answer, the polls, and every error, and an error of a launch that carried secrets keeps only the server's kebab `error`, `detail`, `line`, `source`, and each issue's `rule`, `line`, `column`, `message`, and `hint`. Every decision on an answer (the hash, the id, the status, the error code) reads it as it came, and only the printed copy is redacted, so a short value cannot change an id or a status. In that copy a top-level field hipc checks by shape (`vm_id`, `compose_sha256`, `status`, `boot_phase`, a kebab `error`, a declared name) is printed as it came unless it may be a value sent, every other string is redacted in one longest-first pass, and a key or a number is redacted when it spells a value (a number holding an all-digit value of 8 digits or more included). The message of any launch failure outside 2xx that carried secrets is built from the kept fields alone, and a redirect's target is never shown. A validate answer without `secret_names` is `internal`, and a name is quoted only when the compose declares it; the dry run describes a name the server would not take by its place in the file. The question names `--os-disk-tier` and `--backup-interval` when given.

Text mode escapes the control characters of a message body, as it does every string from the server.

The dry run lists the read, then the `PATCH`. With a membership selected it sends no account header. Attaching a file to a message stays on `hipc api`.

A name is one line of 1 to 64 characters. The routes are personal: whatever account, project, or billing account is selected, no header is sent, so a membership never reaches another user's code, and a list holding links of more than one non-empty code is printed whole, with a warning in text mode.

### Security

- `hipc support tickets create` and `reply` refuse, with `usage` and before anything is sent, a dry run included, a subject or message that holds `HIPPIUS_TOKEN` or a token any profile of the config file stores, as it is, quoted, or percent-encoded: a person reads the ticket, and an injected instruction to "attach the config" would hand them the account. The refusal does not quote the text.
- `hipc` clears its own copies of the API token from memory when it drops them, best effort: the token, a stored token that is replaced or removed, the text the config file is parsed from and written with, and the `Authorization` value. Copies made by libraries, such as the HTTP client's buffers, are not covered. At start it sets its core dump size limit to zero and, on Linux, marks itself not dumpable, so neither a crash dump nor another process of the same user reads the token from it.
- A write to a config file that has another hard link warns once, in text mode, that the other link still holds the old contents, tokens included. The write replaces the file by a rename, so `hipc auth logout` removes the token from one name only, and the rename splits the link, so later writes do not warn.
- `HIPPIUS_TOKEN` is sent only to `https://api.hippius.com`, or to the one origin the new `HIPPIUS_TOKEN_ORIGIN` names, compared as `--api-url` is (scheme and host case, a default port, and a trailing `/` do not matter). A run whose `--api-url`, `HIPPIUS_API_URL`, or profile names another origin withholds it, uses no stored token in its place, and exits 1 `auth` before sending, with a hint naming `HIPPIUS_TOKEN_ORIGIN`; a `HIPPIUS_TOKEN_ORIGIN` that is not an origin is `usage`, naming the variable; before, `--api-url` alone sent the variable to any host.
- `hipc api` sends only to the configured API origin: a full URL on any other, plain `http` to a loopback port included, exits 2 `usage` with a hint to use curl, a dry run included, where before it was sent without the token. Its `--all` still follows `next` links only on the first page's origin and path.
- `hipc api` never sends a request to the account token route `/auth/token/`, on any method, `--reveal` and a dry run included; it exits 2 `usage` before the `--reveal` check, so the refusal is not hidden behind it.
- A `next_step` in the server's answer, at any depth, is dropped from every document `hipc` prints, in JSON and text mode, the record of what was done that a failure prints included: agents are told to run `next_step`, so only `hipc` sets it, on the Drive and S3 card subscribe, `hipc billing auto-reload card-setup`, and `hipc cdn hostnames domain-connect`, each of which drops the server's first. `hipc api` still prints the body as sent.
- Every file flag, such as `--token-file`, `--body-file`, and `--block-body-file`, reads a regular file only, as `--compose-file` did: a symlink is not followed (a public key file, which dotfile managers link, follows it to a target held to the same checks) and a FIFO or a device is refused with `usage` rather than read or waited on, so `/dev/stdin` and `<(...)` are refused too and `-` reads stdin; the help of each flag that reads stdin, and of the cluster key file, says so. The hipc config file and the AWS credentials and config files, at the path the variables name and at the default one, are refused by any path or hard link, and as stdin, so a planted link cannot send the token to support staff or into a WAF block page.
- The Hub double-subscribe marker of every profile in the config file that holds the same origin and token blocks a second subscribe, not only the marker of the profile in use, so `--profile` with a second name for the same token no longer charges a second plan inside the 10-minute window.
- `hipc hub keys create`, `hub keys rotate`, and `hub namespace create` drop the server's `docker login` command fields, which could pass the secret with `-p`, and print `docker_login_command`, built by `hipc` to read the secret from stdin, as `hub namespace robot rotate` does; an answer that holds a `docker login` command elsewhere is refused whole as `internal`, with `partial` side effects. The check of every Hub robot and key answer reads a command as a shell would: through quotes, backslashes, a continued line, a flag or a substitution between `docker` and `login`, and in an object key. A robot or key login that starts with `-`, which `docker login -u` would read as a flag, is `internal` and prints nothing.
- `--ssh-public-key-file` and `ssh-keys create --public-key-file` send only a line in the OpenSSH public key format (a key type such as `ssh-ed25519`, then the key in base64, then an optional comment). Any other one-line file, such as a token, was sent, and the server's refusal echoed it on stderr.
- The new private files `hipc` writes (a kubeconfig, an invoice PDF, a fixed compose, and the database TLS files of `--credentials-dir`) are refused, at parse time and again when created, in a directory another user can write: one owned by another user (but root), or writable by others or by a group other than the user's private group (the primary group with the user's own id, whose umask 002 makes directories 0775), unless it is sticky such as `/tmp`; a 0775 directory of a shared group such as `staff` on macOS is refused. A directory that cannot be opened for reading (mode 0300) is refused too. Such a user could swap `ca.crt` or the kubeconfig for their own, or delete `client.key`. The files are created in the checked directory's open descriptor, and a failed write removes the file through it.
- When the server answers an App Engine launch with a `vm_id` that is a secret value sent, the note, the poll's `--debug` line, the error, and the hint no longer print it: the app is named "the app", and the id is not polled (`internal`, with the redacted answer on stdout).
- A 2xx to `hipc compute databases create` or `restore --reveal` that is not JSON is still `internal`, and its body, cut at 1 MiB, goes on stdout as `{"unparsed_answer": ...}`, since it may hold the only copy of the new database's credentials.
- `hipc api POST /registry/subscribe/` is never sent, a dry run included: it reads no current plan, so it could start a second paid Hub subscription. `hipc hub subscription subscribe` is the path, which refuses a second plan and replaces one only with `--replace`.
- `hipc api` needs `--reveal` on the signed download URL of a chat attachment (`GET /chat/conversations/<id>/attachments/<id>/` and `/support/chat/tickets/<id>/attachments/<id>/`), on `GET` and `POST /databases/<n>/backup-token/`, and on the answers of `POST /auth/sso/ticket/`, `/auth/session/`, `/auth/sign-in-methods/step-up/verify/`, `/network/infra/enroll/`, and `/chat/workspaces/<id>/invites/`, which may hold a session, a ticket, or an invitation.
- An API path with a `;` or a character outside ASCII is refused as `usage` before anything is sent, a dry run included: a front end that drops path parameters or folds characters could deliver it to another route than the one `hipc` classified, such as `/auth/token/;` without `--reveal`.
- A proxy variable (`ALL_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY`, or their lowercase forms) that is not an `http` or `https` proxy URL, such as a SOCKS proxy, is refused as `usage`, naming the variable, instead of being skipped so the request went around it. The first variable set decides, and an empty one counts as unset.
- A 2xx a command refuses has the token redacted and the secret fields dropped from its `details` and `request_id`, as an error answer has.
- Server text quoted in an error message is cut after 512 characters, followed by how many more there are; `details` keeps the whole body, and the token is redacted before the cut, so a cut cannot leave part of it. An `X-Request-Id` over 200 bytes is dropped.
- `install.sh` installs the tarball's `hipc` only when it is a regular file: a symlink member, even in a tarball that matches `SHA256SUMS`, is refused, so the installer never copies and runs a file the link points at.
- The release workflow builds, signs, and publishes a tag only when its commit is on `main`, checked before anything runs and again before the release is created. This catches a tag put on the wrong commit by mistake; the workflow runs from the tagged commit, so only a tag ruleset keeps someone who can push tags from releasing a commit of their own. Its Homebrew job fails, rather than passing with a note, when the tap token is missing in the public repository, so a release whose formula was not updated shows as failed.
- The install one-liner in the README, `docs/getting-started.md`, and `docs/agents.md` is `curl -q --proto '=https' --tlsv1.2 -fsSL <url> | sh`, the line the script's header gives and the way the script downloads: curl reads no `~/.curlrc`, so an `insecure` there does not apply, and no redirect can drop to plain HTTP before the script runs and checks the tarball.
- `hipc api` refuses, with `usage` and before anything is sent, a dry run included, a `POST`, `PUT`, `PATCH`, or `DELETE` under `/api/support/` (a new ticket, a reply, a ticket update, a chat handoff) whose body holds `HIPPIUS_TOKEN` or a token any profile of the config file stores, as it is, quoted, percent-encoded, or behind a JSON escape, as `hipc support tickets create` and `reply` refuse one. The refusal quotes neither the body nor the path, and `refused_when` on `api` in `hipc schema` lists it.

- Before 1.0, `hip network groups`, `hip network policies`, `hip network vpcs resources`, and `hip network vpcs routers` move to `... list` commands, when the writes for those resources are added.
- `hip compute kubernetes`: managed Kubernetes without the cluster key. `clusters list | get | events | refusals` read the clusters, their journal, and the launches refused in the last 7 days; `node-pools list` and `operations list` read a cluster's pools and node operations. `backups <id> --reveal` reads the etcd snapshots, whose download links work without a token. `clusters delete`, `node-pools create`, `operations cancel | resume`, and `nodes delete` are confirmed with `--yes`; the delete reads the cluster first and names it, and a cancel or resume reads the operation first and names its state, its kind, and what it does next. A resume of an operation that is neither `blocked` nor `queued`, and a cancel of one that is `done`, `failed`, or `cancelled`, are refused as `conflict` before the question; so is a resume of an operation blocked on data a node would lose, since only the console can sign that acceptance. Creating a cluster, which generates its key, stays in the console.
- `hip compute kubernetes` with the key file the console saves when it creates a cluster (`hippius-cluster-<name>.key`), passed as `--cluster-key-file <path>`. `clusters kubeconfig <id> --output-file <path>` checks the key file against the cluster, verifies the cluster's signature on its kubeconfig, opens it, and writes it to a new file with mode 0600, never to stdout. `node-pools scale <id> <pool_id> --count <n>` signs one node operation per node added, and needs no key file to scale down. `nodes replace <id> <node_name>` signs the new node, which replaces the old one once it is ready. Both writes read the cluster, its pools, and its operations first, and the confirmation names the pool, the change in nodes, and that each new node is a VM billed to the balance. After the confirmation, both read the pools and the operations again, and refuse as `conflict`, with nothing signed or sent, a pool whose size is not the one the confirmation named (a scale down included, since its count is applied to the pool as it is then), one that signs other params when nodes are added, or a node another operation already removes or replaces. The key file must be a regular file only its owner can read, not a symlink, and at most 1 MiB. The private keys stay in `hip`: they are never sent, printed, or stored.
- `hip api GET /kubernetes/clusters/<id>/backups/` needs `--reveal`.
- `resume`, `scale`, and `replace` join the verb shelf of tenet 2.
- `hip` is licensed under MIT OR Apache-2.0, at your option.
- `scripts/manual_test.sh` and `docs/user-journeys.md`: a guided walkthrough of twelve user journeys against the live API, for a maintainer with a real token. Each scenario starts from a fresh temporary home and logs in and out. The default tier only reads. `--tier write` also creates and deletes a bucket, an S3 sub token, an SSH key, and a Hub key. A cleanup ledger, and account snapshots taken before and after, leave the account as it was found. The token never reaches argv or the log.
- Install channels for 1.0, not yet published: `install.sh`, a POSIX `sh` installer for macOS and Linux that checks `SHA256SUMS`, and its cosign signature when `cosign` is on `PATH`, and installs to `~/.local/bin` or `HIP_INSTALL_DIR` without root; a Homebrew formula in `thenervelab/tap`; and binary-only wheels on PyPI under the name `hippius`, which replace the old Python SDK from 1.0.0 (pin `hippius==0.2.77` to keep it).
